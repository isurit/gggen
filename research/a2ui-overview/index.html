A2UI 개념 정리

서버가 JSON으로 화면을 설명하고 Android가 Compose로 그리는 과정을 살펴봅니다.

A2UI 개념 기본 카탈로그 Figma 예제 커스텀 컴포넌트 Figma와 기획 앱 재배포 조건 시스템 흐름 공식 자료

A2UI는 무엇인가

A2UI(Agent to User Interface)는 서버나 에이전트가 UI의 구조와 값을 JSON 메시지로 전달하는 규약입니다. 앱의 렌더러는 카탈로그에 등록된 컴포넌트를 찾아 네이티브 화면을 그립니다. 레이아웃은 템플릿, 규칙 또는 LLM으로 만들 수 있습니다.

용어그림을 읽는 데 필요한 개념
Surface클라이언트에서 화면을 표시하는 영역입니다. Android Compose에서는 앱이 그 자리에 A2uiSurface를 배치합니다. 기기 목록 전체를 Surface 하나에 담고, 그 안의 List가 여러 Card를 표시할 수 있습니다.
컴포넌트카드나 텍스트처럼 화면을 구성하는 요소입니다.
데이터 모델기기 이름처럼 컴포넌트에 채울 값입니다. 컴포넌트가 데이터 경로를 참조하면 서버는 배치를 유지하면서 해당 값만 갱신할 수 있습니다.
카탈로그렌더러가 사용할 수 있는 컴포넌트와 속성을 정한 계약입니다.

서버와 앱이 주고받는 메시지

문서 예제의 메시지 형식에서는 createSurface가 화면 영역과 사용할 카탈로그를 정합니다. updateComponents는 root부터 자식 ID로 이어지는 화면 구조를 전달하고, updateDataModel은 텍스트나 상태에 바인딩할 값을 보냅니다. deleteSurface는 해당 영역을 제거합니다. 버튼 동작을 서버에 연결한 앱은 사용자의 선택을 액션 메시지로 보내고 후속 화면 변경을 받을 수 있습니다. 공식 메시지 사양

Android에서는 Compose 렌더러와 Material 3 기본 카탈로그가, iOS에서는 A2UI 프로젝트의 SwiftUI 렌더러와 BasicCatalogSwiftUI가 각 플랫폼의 기본 매핑을 제공합니다. 두 앱이 같은 프로토콜과 카탈로그 계약을 지원하면 같은 화면 JSON을 사용할 수 있고, 실제 스타일은 각 앱에서 정합니다. 팀 전용 타입을 공유하려면 지원할 플랫폼마다 렌더링을 연결합니다. 렌더러 목록 · SwiftUI 샘플

기본 카탈로그

컴포넌트는 화면을 구성하는 요소이고, 카탈로그는 어떤 컴포넌트와 속성을 쓸 수 있는지 정한 계약입니다. 예를 들어 Card는 컴포넌트이고, 공식 기본 카탈로그에는 Card가 자식 요소를 child로 받는다는 정의가 들어 있습니다.

서버는 Surface를 만들 때 사용할 카탈로그를 지정하고, 화면을 구성할 때 그 안의 컴포넌트를 골라 보냅니다. 목록에 카드를 열 장 표시해도, 카탈로그의 Card 타입 정의 하나를 열 번 사용하는 것입니다.

카탈로그는 컴포넌트 계약을 묶어 버전으로 관리하는 단위로 볼 수 있습니다. 예를 들어 팀이 ColoredCard의 필수 속성을 호환되지 않게 바꾼다면, v2 카탈로그를 만들어 이를 지원하는 앱에 적용할 수 있습니다. 이때 카탈로그 버전은 팀이 정한 컴포넌트 계약을, A2UI 프로토콜 버전은 서버와 앱이 주고받는 JSON 규칙을 가리킵니다.

이 문서의 기본 카탈로그 표에는 예제 형식에 해당하는 18종이 있습니다. 각 컴포넌트의 화면 예시와 속성을 나란히 볼 수 있습니다. 미리보기는 참고용이며 실제 모양은 앱의 렌더러와 테마에 따라 달라집니다.

같은 컴포넌트도 카탈로그가 허용하는 속성과 값을 조합해 여러 형태로 사용할 수 있습니다. 예를 들어 0.9.1의 Text는 variant: "h3"로 제목을, variant: "caption"으로 보조 문구를 표현합니다. Row는 justify: "spaceBetween"과 align: "center"를 함께 써서 자식을 양쪽에 벌리고 세로 중앙에 맞춥니다.

variant는 일부 컴포넌트가 제공하는 속성 이름입니다. Row처럼 여러 속성을 조합해 배치를 바꾸거나, Card → Column → Text처럼 컴포넌트를 조립해 화면 구성을 바꿀 수도 있습니다. 원하는 색상이나 동작이 현재 계약에 없다면, 테마로 적용할지 컴포넌트를 확장할지 결정합니다.

표는 A2UI 0.9.1 공식 기본 카탈로그 기준입니다. 속성 이름은 JSON의 키이며, 값을 바꾸면 렌더러에 전달하는 동작이나 표현이 달라집니다. id와 component는 공통으로 필요하고, accessibility로 접근성 정보를 전달할 수 있습니다. weight는 Row나 Column의 직접 자식에 주는 상대 비율입니다. 공식 기본 카탈로그 가이드

예: 밝기 슬라이더의 이름을 표시합니다.
checks
조건과 오류 문구의 배열 동작 또는 입력이 조건을 만족하는지 검사합니다.
주의
min과 max는 범위를 정합니다. 일정한 간격으로 멈추도록 하는 steps는 1.0에서 추가됐고, 값 변경을 실제 제어에 쓰려면 동작을 연결해야 합니다.
입력DateTimeInput
브라우저에 따라 선택 UI가 달라집니다
value 필수
ISO 8601 문자열 또는 데이터 바인딩 선택한 날짜·시간을 표시합니다. 미선택 상태는 빈 문자열로 시작할 수 있습니다.
enableDate
true · false 날짜 입력을 활성화할지 정합니다.
enableTime
true · false 시간 입력을 활성화할지 정합니다.
min
ISO 8601 날짜·시간 또는 바인딩 선택 가능한 시작 값을 지정합니다.
max
ISO 8601 날짜·시간 또는 바인딩 선택 가능한 끝 값을 지정합니다.
label
예: 예약 시간 입력의 이름을 표시합니다.
checks
조건과 오류 문구의 배열 동작 또는 입력이 조건을 만족하는지 검사합니다.
주의
enableDate나 enableTime을 켜야 해당 입력을 표시합니다. 데이터에 저장할 ISO 8601 값과 앱에 보여줄 지역별 표시 형식은 구분합니다.

화면에서 이미지나 미디어를 쓰려면 서버가 해당 컴포넌트를 생성할 수 있어야 하고, 앱에는 이미지 로더나 재생 구현이 연결되어 있어야 합니다.

커스텀 컴포넌트

기본 컴포넌트 조합을 재사용하는 방법으로는 서버 템플릿과 카탈로그 확장이 있습니다. 서버 템플릿은 ‘추천 카드’에 제목과 사진을 넣어 기존 Card, Row, Image, Text로 풀어 보냅니다. 카탈로그 확장은 FeatureSuggestionCard처럼 클라이언트가 받는 새 타입과 속성을 정의하고, 그 타입을 그리는 앱 구현을 연결합니다. 두 방법 모두 카드 안에 기본 요소를 조합해 같은 배치를 만들 수 있습니다.

3번 · 에어 케어

3번 Figma 예제에서 화면 구성은 기본 컴포넌트로, 스와이프 동작은 AirCarePager로 구현했습니다. 한 번에 카드 한 페이지를 보여주고, 스와이프하면 다음 페이지와 활성 표시점이 함께 바뀝니다.

기본 컴포넌트와 커스텀의 경계

AirCarePager · 커스텀
├─ 첫 페이지 · Row
│  ├─ 야외 · Column
│  ├─ 거실 · Column
│  └─ 우리방 · Column
└─ 두 번째 페이지 · Row
   ├─ 준우방 · Column
   └─ 침실 · Column

각 공간의 Column 안에는 기호, 이름, 상태를 그리는 Text가 들어갑니다. 여기에 필요한 건 가로·세로 배치와 데이터 바인딩입니다. AirCarePager는 두 Row를 받아 한 페이지씩 표시하고, 제스처와 하단 점을 처리합니다. 앱 구현에는 Compose의 HorizontalPager를 사용했습니다.

서버와 앱이 맞춘 속성

속성서버가 전달하는 값앱에서의 처리
title, subtitle필수 · 제목과 안내 문구. 이 예제에서는 데이터 모델에 연결합니다.페이지 위에 공통 제목과 안내를 그립니다.
firstPage필수 · 첫 번째 Row의 ID첫 페이지에서 야외·거실·우리방을 표시합니다.
secondPage필수 · 두 번째 Row의 ID두 번째 페이지에서 준우방·침실을 표시합니다.

디자인의 동작을 앱에 연결하는 과정

  1. 동작을 정의합니다. 한 화면에 한 페이지를 표시하고, 좌우 스와이프나 하단 점 선택으로 두 페이지를 오가게 합니다.
  2. 앱에 구현하고 등록합니다. AirCarePager가 두 자식 ID를 해석해 페이지를 그리고, 현재 페이지와 표시점을 함께 갱신하도록 구현합니다. 기본 컴포넌트와 함께 앱 카탈로그에 등록합니다.
  3. 서버가 페이지 내용과 값을 보냅니다. createSurface로 커스텀 타입이 들어 있는 카탈로그를 지정하고, 두 페이지의 구조와 공간별 값을 전달합니다. 페이지 전환은 받은 데이터로 앱에서 처리합니다.

이미 등록된 속성 범위에서는 공간 이름이나 상태, 각 페이지 안의 구성은 서버에서 바꿀 수 있습니다. 앱 구현이 받는 페이지가 두 개로 정해져 있으므로, 세 번째 페이지까지 지원하려면 페이지를 받는 계약과 앱 구현을 함께 변경해야 합니다.

4번 · 기능 제안

4번 미리보기의 제목·사진·문구 배치를 FeatureSuggestionCard 하나에 묶었습니다. 여러 추천에서 같은 모양을 쓰고 값만 바꿀 수 있도록, 카드 내부 배치는 앱에서 관리합니다.

필수 속성예시 값카드에 표시되는 위치

서버는 Surface의 커스텀 카탈로그를 지정하고 세 값을 데이터 모델에 담습니다. 앱에 등록된 FeatureSuggestionCard는 그 값을 읽어 내부에서 Compose Card 계열과 Column, Row, 이미지, 텍스트를 조합합니다.

3번은 페이지 전환 동작을 구현하기 위해 커스텀 타입을 썼습니다. 4번은 기본 카탈로그로도 표현할 수 있는 배치를 공통 카드로 재사용하기 위해 커스텀 타입으로 등록한 예입니다. 사진 변경 범위는 앱의 이미지 로더가 지원하는 주소에 따릅니다.

기획과 Figma에서 확인할 것

디자이너는 Figma에서 팀의 기기 카드·배지·리포트처럼 설계하기 편한 단위로 작업합니다. 개발팀은 그 요소를 앱에서 지원하는 A2UI 컴포넌트와 속성에 대응시킵니다. Figma 카드 하나가 여러 A2UI 요소로 변환될 수 있습니다.

디자인 요구표현 방법구현 시 확인
기기 이름과 종류를 세로로 배치Card → Column → Text + Text긴 이름의 줄바꿈과 빈 값 표시

요일별 상태 점과 작은 배지기본 배치를 활용하고 상태의 색·형태는 전용 속성이나 컴포넌트로 표현원본과 일치해야 하는 스타일, 상태별 데이터, 접근성

변환 전에는 카탈로그의 속성 → 서버 변환 범위 → 앱의 렌더링과 동작을 확인합니다. 에이전트는 Figma 구조를 읽어 지원되는 요소로 매핑하고 빠지는 부분을 표시할 수 있습니다. JSON 검증 뒤에는 작은 화면, 긴 텍스트, 빈 데이터로 실제 앱 화면을 비교합니다.

앱 재배포가 필요한 경우

이미 배포된 앱이 지원하는 배치와 데이터는 서버 JSON으로 바꿀 수 있습니다. 화면을 그리거나 동작시키는 기능을 앱에 처음 추가하는 경우에는 그 구현을 포함한 앱을 배포해야 합니다.

어떤 변경을 서버에서 처리할 수 있나

판단할 때는 “이 디자인이 새로운가?”보다 “사용자가 설치한 앱이 필요한 요소를 그리고, 요청한 동작까지 수행할 수 있는가?”를 먼저 봅니다. 처음 선보이는 화면도 기존 요소와 동작을 조합해 표현할 수 있으면 서버에서 배포할 수 있습니다.

바꾸고 싶은 것서버에서 처리할 수 있는 예앱 업데이트가 필요한 예
내용과 노출 조건공지 문구나 상품 가격을 바꿉니다. 주문 상태가 ‘배송 중’이면 배송 안내를 추가합니다. 서버가 값을 알고 있고 앱이 기존 텍스트로 표시할 수 있습니다.사용자의 현재 위치에 맞는 공지를 보여주려는데 앱에 위치 권한 요청과 위치 전달 기능을 처음 넣어야 합니다.
배치와 순서예약 화면에서 취소 안내를 결제 정보 위로 옮기거나, 카드의 사진과 설명을 가로에서 세로로 재배치합니다. 서버가 각 요소의 순서와 배치를 지정할 수 있는 경우입니다.앱 내부에 배치가 고정된 전용 카드에서 사진을 본문 위에 겹쳐야 합니다. 기존 속성이나 다른 등록 요소의 조합으로도 겹침을 표현할 수 없으면 앱에 그 배치를 추가합니다.
목록과 페이지 수추천 상품을 3개에서 5개로 늘립니다. 항목 목록을 받는 컴포넌트라면 서버가 항목 두 개를 더 보냅니다.두 페이지만 받도록 구현된 스와이프 카드에 세 번째 페이지를 추가합니다. 같은 카드 안에서 세 페이지를 넘기려면 앱이 가변 개수의 페이지를 처리할 수 있어야 합니다.
이미지와 스타일배너 사진을 앱이 이미 읽을 수 있는 주소의 새 사진으로 교체합니다. 카드가 ‘강조’ 스타일을 지원한다면 특정 배너에만 적용할 수 있습니다.사진 영역이 앱 코드에서 세로형으로 고정돼 있는데 정사각형 썸네일이 필요합니다. 기존 배치나 속성으로 영역의 비율을 지정할 수 없다면 이미지 표시 구현을 확장합니다.
버튼과 사용자 동작주문 카드에 ‘배송 조회’ 버튼을 추가합니다. 앱이 배송 상세 화면 열기를 이미 지원하면 서버가 버튼에 그 동작과 주문 번호를 연결합니다.‘영수증 촬영’ 버튼을 눌러 카메라를 열고 사진을 첨부해야 하는데 앱에 그 동작이 없습니다. 버튼은 그릴 수 있어도 촬영·첨부 기능은 앱에 구현해 배포해야 합니다.

여러 앱 버전을 함께 운영하면 같은 디자인도 버전별로 판단합니다. 예를 들어 새 버전에는 스와이프 카드를, 이전 버전에는 같은 내용을 기존 목록으로 보낼 수 있습니다. 이때 서버는 요청한 앱이 어느 구성을 지원하는지 구분할 수 있어야 합니다.

Surface와 카탈로그를 한 번 연결한다는 뜻

앱은 먼저 메시지 프로세서에 렌더링 카탈로그를 연결합니다. 이후 서버가 지원 범위 안의 JSON을 보내면 앱은 같은 호출로 새 구성을 그립니다. 새 화면마다 Compose 화면 코드를 만드는 작업이 줄어드는 지점입니다.

// 초기 연결에서 앱이 지원할 카탈로그를 선택
val processor = A2uiMessageProcessor(catalogs = listOf(basicCatalog))

// 수신한 JSON 메시지를 처리하고 활성 Surface 모델을 표시
processor.processInput(parser, rawMessage)
A2uiSurface(surfaceModel = surface)

이미지의 경우 JSON의 Image.url은 사진의 주소입니다. 이 예제의 AndroidX Material 연결에서는 기본 Image가 전달한 주소와 표시 속성을 앱이 연결한 이미지 로더가 받습니다. 앱 쪽 콜백이 사진을 내려받아 그려야 실제 이미지가 보입니다. 초기 앱은 이 콜백이 비어 있었고, 이후 한 번 연결했습니다. 지금 앱에는 외부 요청이 느리거나 실패할 때 쓸 예시 사진도 포함되어 있습니다.

카탈로그를 서버에서 받는 경우 카탈로그 정의를 전달하면 이름과 속성 규칙을 공유할 수 있습니다. 앱에 그 타입을 실행하는 구현이나 실행 가능한 템플릿 기능이 갖춰져 있어야 화면에 그릴 수 있습니다. 4번처럼 기본 요소의 조합이면, 서버에서 템플릿을 관리하고 기존 Card, Row, Image, Text로 풀어 보내는 방식도 가능합니다.

Figma를 수정하면 언제 앱에 반영되나

  1. Figma 변경을 읽습니다. 꼭 유지해야 하는 배치, 속성, 동작을 기록합니다.
  2. 현재 앱의 카탈로그에 맞춰 변환합니다. 필요한 컴포넌트가 등록돼 있는지, 원하는 속성과 동작을 실제로 처리하는지 확인합니다.
  3. JSON과 렌더링을 검증합니다. 필수 속성과 자식 ID를 확인하고, 실제 화면에서 글자 길이·이미지 크기·동작을 살펴봅니다.
  4. 서버에 반영합니다. 현재 데모는 정리한 디자인 스냅샷을 사용합니다. 최신 스냅샷을 저장하고 선택하면 앱의 다음 새로고침에 적용됩니다.

Figma 원본의 변경을 저장 시점에 앱까지 자동으로 전달하려면, 변경 감지와 변환·검증·반영 과정이 추가로 연결되어야 합니다.

4번에서 APK를 여러 번 빌드한 이유

버전추가한 기능배포가 필요한 범위
0.5기본 Image에 URL 이미지 로더 연결기존 앱에서 사진을 처음 표시하려면 앱 업데이트가 필요했습니다.
0.64번을 FeatureSuggestionCard로 등록커스텀 타입을 쓰는 실험에 필요한 빌드였습니다. 기본 컴포넌트 조합으로도 같은 카드 배치를 표현할 수 있습니다.
0.7앱이 서버에 새 타입 지원 여부를 알리도록 연결서버는 지원 신호가 없는 앱에는 기본 조합을 보냅니다. 이 응답 변경은 기존 앱에서 새 타입을 찾지 못하던 오류를 서버 쪽에서 해결합니다.
0.8외부 사진을 기다리거나 가져오지 못할 때 쓸 예시 사진을 앱에 포함앱에 내장 사진을 추가한 빌드입니다. 이미 URL 사진을 표시할 수 있는 앱은 문구나 배치를 바꾸기 위해 이 빌드가 필요하지 않습니다.

프로젝트 시작 전에 확인할 범위

  • 자주 바뀌는 항목을 정합니다. 문구, 카드 순서, 가로·세로 배치, 이미지 비율처럼 반복해서 바꿀 항목을 Figma 요구사항에서 표시합니다.
  • 설치된 앱에서 되는지 확인합니다. 공식 카탈로그에 이름이 있어도 앱의 이미지 로더나 이벤트 처리기가 실제로 연결돼 있어야 합니다.
  • 앱 버전별로 보낼 화면을 정합니다. 새 타입이 등록된 앱에는 새 구성을 보내고, 기존 앱에는 같은 정보를 기본 조합으로 보냅니다. 4번이 이 방식의 예입니다.
  • 직접 만든 JSON 방식과 비교합니다. 둘 다 JSON에서 Compose 요소를 조립합니다. A2UI를 쓰면 공통 카탈로그, 메시지 구조, Surface 갱신 방식과 기존 렌더러를 재사용할 수 있습니다.
